# Android 客户端与云端重构方案

日期：2026-10-21。本文保留总体重构设计；用户后续已确定当前使用 HTTP、客户端本机开发打包、不进行模拟器安装验证。实际试用版实现与交付范围以 ANDROID-DELIVERY.md 为准。

Android 页面、代码分层、同步实现和客户端里程碑详见 [ANDROID-CLIENT-PLAN.md](./ANDROID-CLIENT-PLAN.md)。

## 1. 已确认事实与待确认信息

- 当前仓库是 Next.js 网站，包含公开博客、单所有者工作台、Route Handler API、Prisma/SQLite 和本地附件存储。
- 用户已澄清当前不使用 Expo Go。仓库没有现成移动工程，需要新增 Android 客户端，不再查找另一个 Expo Go 工程。
- 云服务器：阿里云 ECS e 实例，公网 IP `121.43.32.47`，2 核 CPU / 2 GB 内存；用户原报 Ubuntu 22.04，2026-10-21 通过 SSH 实测为 Ubuntu 24.04.5 LTS / x86_64。无域名，已使用用户授权的 root 密码完成 SSH 只读检查；尚未配置专用部署密钥。
- 服务器已有 `personal-garden.service`，监听 `127.0.0.1:13300`，本机 HTTP 检查返回 200。云端 package.json 包含本地没有的 AI SDK 依赖，不能直接用当前本地快照覆盖。详情见 [SERVER-INSPECTION.md](./SERVER-INSPECTION.md)。
- 已确定开放多用户独立注册，现有单所有者模型必须改造。
- 注册采用固定邀请码准入：只有输入 `LOVEXCZ` 且其他注册条件通过时才可创建账号；规则详见第 6 节。
- 已确定全部业务记录同步云端，手机保存离线副本；设备设置与缓存仅保存在本地。不提供逐条记录选择是否同步的功能。
- Expo / React Native 是拟采用的开发工具链，不等于要求用户安装 Expo Go；实际交付为独立签名 APK。

## 2. 建议架构

```text
Android App（Expo / React Native）
  ├─ 原生页面、编辑器、文件选择
  ├─ SQLite：业务记录、本地草稿、待同步操作
  ├─ 应用文件目录：附件原件、离线文件
  ├─ SecureStore：设备登录凭据
  └─ HTTPS API + 同步客户端
                 │
                 ▼
云服务器 121.43.32.47
  ├─ HTTPS 反向代理
  ├─ Next.js：现有公开博客、网页工作台、移动端 API
  ├─ 业务数据库：同步记录、发布快照、会话、同步变更
  └─ 持久化附件目录、备份任务
```

Android App 不直接连接云端数据库。电脑只承担开发和构建，正式安装包运行时不依赖电脑或 Expo Go。

建议保留 Next.js 后端，不同时引入独立后端框架。云端数据库以 PostgreSQL 为目标，手机使用 SQLite；部署资源和连接池参数待服务器配置确认后确定。两端数据库通过 API 同步记录，不能互相覆盖数据库文件。当前 SQLite 的迁移 SQL 不能直接作为 PostgreSQL 迁移运行，需要建立新迁移基线并执行数据转换验证。

## 3. 代码组织与复用边界

初期保留现有根目录 Next.js 工程，新增目录，减少同时搬迁整个仓库的风险：

```text
src/                    现有网站、服务端入口与业务逻辑
prisma/                 服务端数据模型和迁移
apps/mobile/            Expo Android 工程
packages/contracts/     可共享的 DTO、Zod 校验、枚举、错误码
deploy/                 生产 Compose、反向代理和运维配置
```

共享契约应保持纯 TypeScript，不引用 Next.js、Node.js、Prisma 或 React Native。使用工作区管理依赖时需重新生成并验证锁文件。

- 可以提取复用：记录类型、状态、字段约束、接口协议、部分纯业务函数。
- 服务端继续使用：Prisma、scrypt、文件系统、发布快照、备份恢复。
- 手机端重新实现：导航、列表、表单、Markdown 编辑与预览、附件选择、离线状态。
- 当前组件中的 HTML、CSS、window 和 localStorage 不能直接作为 React Native 界面使用。

## 4. 已确定的数据存储边界

| 类型 | 手机 | 云端 | 内容 |
| --- | --- | --- | --- |
| 仅本地 | 持久保存，缓存可重建 | 不上传 | 主题、字号、设备偏好、下载缓存等 |
| 云端同步 | 保存离线副本及待提交修改 | 保存按用户隔离的已确认版本 | 全部业务记录、草稿、关联、附件、复盘及历史 |
| 云端公开 | 按需缓存 | 保存明确发布的独立版本 | 文章、作品、推荐、公开附件 |

“上传云端”和“公开发布”是两种不同权限。同步的私密记录仍必须登录才能访问。现有“独立公开稿 → 明确发布 → 不可变快照”的边界应保留。

不增加 `storagePolicy` 或逐条同步开关。本地维护 `syncStatus`、服务端版本与待提交操作；公开状态继续由 Publication / PublishedVersion 管理。离线草稿在本地立即保存，联网后进入同一套同步流程。公开个人资料、账号安全配置和公开稿设置属于服务端业务数据；“设置仅本地”指主题、字号等设备偏好。

附件独立管理同步状态。已上传的离线附件副本可按缓存策略清理，尚未上传的原件和未确认修改不能被清理。记录、关联和复盘快照仅允许引用同一用户有权限访问的业务对象；快照生成逻辑仍应保持历史证据不可变。

手机采用 expo-sqlite 保存结构化数据，文件目录保存附件，SecureStore 保存小体积认证凭据。SQLite 默认不能视作加密数据库；如要求本地数据库加密，应另外评估 SQLCipher、密钥恢复和自定义构建。

云端备份覆盖全部已同步业务数据。手机仍需保护未同步修改，并显示“待同步／同步中／已同步／冲突”状态；不能把“本地保存成功”显示成“云端已备份”。Android 系统备份策略应显式配置，凭据不随普通业务备份导出。

## 5. 离线与同步协议

最小可用流程：

1. 在 SQLite 事务中同时保存编辑结果和 outbox 操作，界面立即显示本地结果。
2. App 前台打开、恢复联网或手动同步时提交 outbox；后台同步只作为后续增强，不承诺操作系统持续运行任务。
3. 每项操作带稳定的 `operationId`、记录 UUID 和 `baseVersion`。服务端幂等处理重试，返回对应操作结果和新版本。
4. 服务端使用有序变更游标提供增量拉取，不依赖手机时间戳；拉取包含删除标记。
5. 手机在事务中应用已确认结果和变更，再推进游标；失败可安全重试。
6. 服务端版本不匹配时保留本地与远端内容，提供比较、合并或另存副本，禁止静默覆盖。

待新增契约示例：`POST /api/v1/sync/push`、`GET /api/v1/sync/pull?cursor=...`。发布操作仍是独立的在线命令，不随普通同步自动执行。

现有 version、Revision、deletedAt 和 409 冲突机制可以复用，但还缺少持久化 outbox、服务端变更日志、幂等记录、游标分页、首次全量同步以及同步元数据过期后的重新同步协议。不能仅复制现有列表接口就宣称完成离线同步。

附件按独立任务上传，云端确认文件完整后再确认业务引用。同步失败保留原件，重试不重复创建附件。发布前必须确认所选公开附件均可用。

云端确认版本决定同步顺序，手机未同步修改必须保留到明确确认或用户处理冲突。注销或切换账号前若存在待同步修改，要提供继续同步或保留隔离副本的选择；不得把前一账号的数据展示或提交给后一账号。

## 6. 移动端认证与多用户必做项

当前 auth.ts 通过 next/headers 读取 Cookie，写接口要求 Origin。原生请求通常没有浏览器 Origin，因此移动端需要单独的认证入口与受保护路由。

建议增加短期访问凭据与可轮换、可撤销的设备刷新凭据；刷新凭据存于手机 SecureStore，服务端只存其哈希，支持注销设备。移动端用 Authorization 请求头认证。网页 Cookie 会话及其 Origin/CSRF 防护继续保留，不能为了兼容 App 全局关闭来源校验。

API 基础地址可以写入 `EXPO_PUBLIC_API_URL`，它是公开配置。数据库密码、SSH 密钥、管理员凭据和第三方服务密钥只能留在服务端。

开放多用户注册，需要先完成：

- Owner 改为 User / DeviceSession；记录、标签、设置、附件、历史、发布稿和同步日志按用户隔离。
- 所有查询、修改、关联目标及附件读取校验归属；不能只在 Record 上加 userId。
- 重复行动、唯一标签名、slug 及登录限速按产品规则重新定义约束。
- 现有所有者数据迁入指定用户，补充两个用户间无法交叉读写的测试。
- 注册、登录、退出、凭据刷新和设备会话撤销形成完整流程；注册和登录分别限速，错误信息避免暴露敏感账号状态。
- 服务端从已验证身份取得 userId，不信任客户端在请求体中声明的数据归属；同步游标、幂等键及后台任务同样按用户隔离。
- 面向普通用户的导出和恢复仅作用于本人数据，不能继续暴露现有全库备份接口；服务器管理员备份与用户导出分开。

原公开博客可继续保留，但“谁能发布到站点首页、普通用户是否有独立公开主页”尚未确定。多用户注册本身不授予站点管理权限；对外发布功能需先明确这一产品规则。

### 6.1 注册邀请码规则（用户已确定）

- 注册表单包含必填的“邀请码”输入框，通过注册请求的 `inviteCode` 字段提交。邀请码为固定的 `LOVEXCZ`，区分大小写；初期作为可重复使用的准入码，不增加一次性消耗或邀请关系功能。
- 服务端保存配置 `REGISTRATION_INVITE_CODE=LOVEXCZ`，仅由服务端注册逻辑读取，不使用 NEXT_PUBLIC / EXPO_PUBLIC 前缀，不将正确答案打包进客户端校验代码、提示文字或接口响应。
- 邀请码缺失或错误时返回明确错误“请输入邀请码”或“邀请码不正确”，且不创建用户、不生成会话、不初始化业务数据；服务端配置缺失时关闭注册，不能跳过校验。
- 邀请码正确仅代表通过准入检查，仍需校验账号、密码和账号唯一性，并使用安全密码哈希。账号创建及必要的初始化保持事务一致。
- 所有注册入口共用服务端校验，直接调用 API 也无法绕过；客户端校验只改善提示体验。注册接口添加限速，日志不记录邀请码、密码或请求原文。
- 邀请码用于注册，已有用户正常登录不重复要求邀请码。邀请码不授予管理员身份，也不允许访问其他用户数据。
- 验收覆盖：缺失邀请码、错误邀请码、大小写不匹配、正确邀请码成功注册、正确邀请码但账号/密码不合格、绕过表单直接请求、服务端配置缺失、重复账号和限速。所有失败路径验证无新增用户及会话。

当前仓库仍无多用户注册入口，本条为已确认实现要求；应与 User / DeviceSession、逐用户权限和注册流程一起交付，不能视为当前已上线功能。

## 7. 服务器部署

初期以 `https://121.43.32.47` 为目标 API 来源，申请公网 IP 证书，不要求先购买域名。Let's Encrypt 已开放 IP 证书，有效期为 160 小时，必须自动续期并在续期成功后重新加载反向代理；可按官方指引使用支持 IP 地址及 shortlived profile 的 Certbot 版本。申请前要验证公网挑战路径可达，最终在真机上确认 TLS 信任。未来有域名时可以迁移 API 来源。仅有 IP 不代表服务已部署，本文也未声称证书已申请成功。

2 核 / 2 GB 作为开发和小规模试用的初始资源配置，容量以压测与监控为准。优先在电脑或 CI 构建 Linux 目标镜像，在 ECS 仅拉取并运行镜像；Android APK 在电脑或构建服务生成。云端只运行反向代理、一个应用实例和 PostgreSQL，控制连接池、上传体积与日志占用，不同时引入 Redis、独立搜索、常驻构建任务等服务。swap 如需启用应先核对磁盘与系统状态，不能作为容量保证。

沿用并扩展现有 Docker Compose：

以下为原拟部署方案。实测服务器已有 systemd 管理的应用及宝塔面板，实施时优先核对并适配现有部署方式；Docker 不是必须条件。本次未修改服务、数据或防火墙，也未申请证书。

- 反向代理对公网提供 443，80 用于按需跳转或证书验证；应用端口和数据库不直接暴露公网。
- 配置 SITE_URL、持久化数据库与附件卷、健康检查、重启策略和日志轮转。
- 数据库与附件使用一致的备份方案，保留异机副本，并实际验证恢复。
- 部署前备份，执行迁移后验证；回滚必须兼顾数据库版本，不能只回退容器镜像。
- 私密上传目录不直接映射为公开静态目录，继续通过鉴权接口读取。
- 手机只连接服务端 HTTPS API；服务器不需要运行 Expo 开发服务器。

首次操作通过阿里云控制台 Workbench 登录，配置本机 SSH 公钥并验证连接。安全组中的 SSH 管理端口只允许可信来源，80/443 用于 Web 服务及证书验证，3000/5432 不向公网开放。具体步骤见 [SERVER-BOOTSTRAP.md](./SERVER-BOOTSTRAP.md)。连接后检查磁盘、CPU 架构、已有服务与端口，再确定构建平台和部署参数。不要把服务器密码提交到仓库或移动安装包。

## 8. Android 安装包与下载

新增 Expo / React Native 移动工程，配置稳定 applicationId、versionCode、图标和 API 地址。用户无需安装 Expo Go。可用 EAS Build 生成签名 APK，也可配置本机 Android SDK/JDK 后本地构建。

直接下载对应的 eas.json 配置示例：

```json
{
  "build": {
    "preview": {
      "distribution": "internal",
      "developmentClient": false,
      "android": { "buildType": "apk" }
    },
    "production": {}
  }
}
```

在移动工程目录完成 EAS 项目和签名配置后执行 `eas build -p android --profile preview`，得到可直接安装的 APK；Google Play 分发通常使用 AAB。构建可能使用第三方云构建额度，应在执行前确认账户与费用条件；本地构建可作为替代。

发布构建应包含运行所需代码，安装后不依赖 Metro 开发服务器。保管签名密钥，后续版本使用相同签名并递增 versionCode。APK 可以放在服务器的独立下载目录，通过 HTTPS 下载页提供版本说明与文件校验值。直接下载安装并不等于完成应用商店发布。

## 9. 分阶段交付与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 1. 多用户服务端基础 | User / DeviceSession、数据库迁移、逐用户权限、接口契约 | 两个用户无法交叉读写记录、附件、历史或备份 |
| 2. 云端 API | 邀请码注册及移动认证、复用现有记录和发布服务、部署配置 | 错误邀请码无法创建账号；断开电脑后手机可通过移动网络访问云端 |
| 3. Android 在线版 | 注册登录、今日、课程/项目、记录编辑、附件 | 签名 APK 独立启动，现有网站仍可使用 |
| 4. 本地与同步 | 本地数据库、outbox、增量同步、冲突处理 | 飞行模式创建/编辑，联网后正确同步；重试无重复 |
| 5. 发布交付 | 下载页、备份恢复、升级验证 | 安装升级保留数据，撤回后公开内容和附件失效 |

关键回归场景包括：两用户权限隔离、两设备同时编辑、删除后离线设备重连、上传中断、App 在本地提交后被终止、账号切换时未同步数据隔离、设备凭据撤销、恢复备份后的同步游标处理。每阶段只宣称实际测试通过的范围。
